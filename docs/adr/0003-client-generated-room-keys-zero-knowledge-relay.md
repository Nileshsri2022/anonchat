# 0003. Client-Generated Room Keys; the Relay Never Holds Key Material

## Context
Until now a "public" Room's key was derivable by anyone who knew the Room identifier (identifier + a constant string), so public-room encryption was decorative: joining by ID alone meant decrypting by ID alone. Real confidentiality for passphrase-less Rooms requires key material that is not derivable from anything the Relay knows.

## Decision
Every Room's Room Key is generated by the Room creator's client (random AES-256 key). It is distributed only out-of-band via an Invite (QR or copyable string) — never through the Relay, never derived from the Room ID. Passphrase-protected Rooms keep PBKDF2 + Room Canary (ADR-0002) unchanged; random-key Rooms are the default. The Relay's invariant is therefore total: it stores and forwards opaque envelopes and never holds, derives, or verifies key material for any Room.

## Considered Options
- Keep ID-derivable keys for "public" rooms (rejected: no confidentiality at all).
- Server-side key escrow with access control (rejected: breaks the zero-knowledge invariant and creates a target).

## Consequences
- Joining a random-key Room requires an Invite, not just a Room ID; the ID alone grants only discovery, not readability.
- Room IDs no longer need to be high-entropy for confidentiality (they stay unguessable for anti-spam).
- This supersedes ADR-0002's note that unprotected rooms "use the default salt": the fallback derivation path is removed.
